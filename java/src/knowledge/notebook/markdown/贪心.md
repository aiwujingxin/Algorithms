# 贪心算法（Greedy Algorithm）六维深度解析：从局部最优到全局最优的信仰与证明

> **一句话总纲**：贪心的全部魅力与全部风险，都凝结在一个大胆的赌注里——「每一步都选当下看起来最好的，最后就能得到全局最好的」。这个赌注在活动选择、最小生成树上稳赢，在 0-1 背包上必输。所以学贪心真正要学的不是「怎么贪」，而是「**凭什么敢贪**」。

---

## 一、缘起与直觉 (Origin & Intuition)

### 1.1 痛点溯源：贪心为谁而生

许多最优化问题的朴素解法是**穷举**：从 `n` 个元素里挑子集、排顺序、做决策，解空间往往是 `2^n` 或 `n!` 级别的指数爆炸。回溯法「尝试—撤销—再尝试」能保证正确，但慢得无法接受;动态规划（DP）通过「记忆化子问题」把它压到多项式级，代价是要维护一张可能很大的状态表。

贪心提出了一个更激进的设想:

> **如果每一步的「局部最优选择」恰好能拼接成「全局最优解」，那我根本不需要回溯、不需要状态表，一次遍历就能出答案。**

这就是贪心的历史定位——它是最优化问题里**「最省」的一档解法**:省时间（通常 `O(n log n)`，主要花在排序）、省空间（常数级或线性）,代价是**适用范围最窄、正确性最需要证明**。

| 范式 | 决策方式 | 典型复杂度 | 适用前提 |
|---|---|---|---|
| 暴力 / 回溯 | 尝试所有可能，可撤销 | 指数级 | 总是正确，但慢 |
| 动态规划 | 保留所有子问题的最优再合并 | 多项式 | 最优子结构 + **重叠子问题** |
| **贪心** | **每步只做一个不可撤销的最优选择** | **`O(n log n)`** | 最优子结构 + **贪心选择性质** |

### 1.2 心智钩子:一眼认出贪心

刷题时出现以下信号，请立刻把贪心列入候选:

- 🎯 求「**最多能选几个 / 最少需要几个 / 最大或最小的某个值**」，且**只要一个数值答案**（而非所有方案）。
- 🎯 元素**可排序**，排序后能一次遍历决策。
- 🎯 涉及**资源分配、区间调度、字典序构造**。
- 🎯 局部最优选择直观，且能构造证明（或怎么都构造不出反例）。

⚠️ **反信号**:需要「整数个组合」「恰好凑出某值的方案数」「不可切分的 0-1 选择」→ 多半是 DP。

> 记忆口诀:看到「优先级」想到堆，看到「区间」想排序键,看到「可切分/连续/可复用」倾向贪心;看到「整数个/不可分/要凑组合」警惕 DP。

### 1.3 物理映射与信息论:贪心的降维打击本质

贪心如何打破信息熵的限制、实现时间复杂度的降维打击?**它用一个单调收敛的标量,压缩掉了整个搜索空间。**

以 **LC 55 跳跃游戏** 为例:判断能否从起点跳到终点，看似需要 BFS/DFS 搜索所有路径（指数级）。但贪心只维护一个标量 `maxReach`(当前能到达的最远右边界)。深层洞察是——**可达性是连续的**:如果你能到位置 5，那么 0~5 之间所有位置都可达（可以选择跳更少）。于是「哪些位置可达」这个指数级信息，被「最远能到哪」这一个整数完整刻画，指数级搜索坍缩为 `O(n)` 扫描。

> **贪心的哲学本质,不是「贪」,而是「舍」。** 它的真正智慧在于:你能证明放弃某些可能性不会让答案变差。贪心是一种「安全的剪枝」——在搜索空间中大刀阔斧砍掉无数分支,而每一刀都砍得恰到好处,不会误伤最优解。

### 1.4 一个反例，看清贪心的边界

**分数背包 vs 0-1 背包**——理解贪心边界的黄金案例。

- **分数背包(可切分)**:按「单位重量价值」从高到低装,装满为止。✅ **贪心正确**,物品可切分,最后一件塞不下切一部分即可,局部最优严丝合缝拼成全局最优。
- **0-1 背包(不可切分)**:同样策略**会失败**。反例:容量 10,物品 `(重6,值10)、(重5,值9)、(重5,值9)`。按性价比贪心选第一件,剩余容量 4 装不下任何东西,总值 10;但最优解是后两件,总值 18。**「不可切分」破坏了贪心选择性质,必须上 DP。**

## 二、结构解剖与动态演变 (Anatomy & Dynamics)

贪心不是一种数据结构,而是一种**算法范式**。它的「结构」体现为**两大成立基石 + 四条底层维度 + 一套动态演化模型**。

### 2.1 核心 API 与时空矩阵

贪心的「操作」是抽象的决策原语,其复杂度取决于承载它的数据结构:

| 操作原语 | 承载结构 | 最好 | 平均 | 最坏 | 空间 |
|---|---|---|---|---|---|
| 排序后线性决策 | 数组 | `O(n log n)` | `O(n log n)` | `O(n log n)` | `O(1)`~`O(n)` |
| 动态取极值 | 堆 (PriorityQueue) | `O(n log n)` | `O(n log n)` | `O(n log n)` | `O(n)` |
| 单调序列维护 | 单调栈 | `O(n)` | `O(n)` | `O(n)` | `O(n)` |
| 反悔/撤销 | 堆(维护已选集) | `O(n log n)` | `O(n log n)` | `O(n log n)` | `O(n)` |
| 覆盖边界推进 | 双指针/标量 | `O(n)` | `O(n)` | `O(n)` | `O(1)` |

绝大多数贪心的瓶颈在**排序**(`O(n log n)`),排序后往往只需一次线性扫描。

### 2.2 结构不变量 (Structural Invariant):贪心合法性的绝对法则

不变量是算法世界的「宪法」——无论执行到哪一步,这个性质永远为真。**对贪心而言,不变量就是每一步选择之后,系统仍然满足的那个核心承诺。** 贪心像在走钢丝,不变量就是钢丝本身:你可以左摇右摆(做各种决策),但只要脚踩在钢丝上(不变量成立),就不会掉下去(偏离最优解)。

贪心成立的**两大数学基石**同样是不变量的一部分:

**① 贪心选择性质 (Greedy-Choice Property)** — 与 DP 的分水岭
> 存在一个全局最优解,它包含了当前这一步的贪心选择。贪心敢在**当下就拍板**,且永不反悔。

**② 最优子结构 (Optimal Substructure)** — 与 DP 的共同前提
> 一个问题的最优解包含其子问题的最优解。做出贪心选择后,原问题缩小为一个**同构的子问题**。

> ⚠️ **关键区分**:最优子结构是贪心和 DP 的**共同**前提;真正把两者区分开的是**贪心选择性质**。DP 之所以保留多个子问题状态,正因为它不具备「当下就能拍板」的贪心选择性质。

围绕不变量,贪心可归纳为**四个底层维度**(全文的骨架):

| 维度 | 一句话概括 | 回答的问题 |
|---|---|---|
| **不变量 (Invariant)** | 贪心过程中始终成立的「约束承诺」 | 我该维护什么量,使局部信息足以做全局判断? |
| **安全点 (Safe Point)** | 当前选择为何不会错过最优解 | 为什么我的贪心选择不会堵死未来? |
| **瓶颈 (Bottleneck)** | 限制答案上/下界的核心约束 | 谁在卡脖子,决定了答案的天花板/地板? |
| **最值 (Extremes)** | 用「极端」来驱动决策的思维范式 | 谁在支配谁,如何沿支配链做线性决策? |

> **四者的关系**:不变量告诉你「维护什么」,安全点告诉你「为什么能这么维护」,瓶颈告诉你「什么在限制答案」,最值告诉你「怎么驱动每一步决策」。

### 2.3 动态可视化:三种最复杂操作的内部演变

**① 补丁型贪心的「翻倍」演变(LC 330 按要求补齐数组)**

维护 `reach`,表示当前已能构造 `[1, reach-1]` 内所有整数。遇到断档时补入 `reach` 本身,覆盖范围**翻倍**:

```text
目标 n=20, nums=[1,5,10]
reach=1  ────────────────────────────────────────────
 nums[0]=1 ≤ 1 → 吸收    reach: 1  →  2      [1,1] 已覆盖
 nums[1]=5 > 2 → 断档!   补 patch=2          reach: 2 → 4   (翻倍)
                          再看 5 > 4 → 断档!   补 patch=4          reach: 4 → 8   (翻倍)
 nums[1]=5 ≤ 8 → 吸收    reach: 8  →  13
 nums[2]=10 ≤ 13→ 吸收   reach: 13 →  23 ≥ 20+1  ✅ 完成
补丁数 = 2   (补了 2 和 4)

覆盖区间演变: [1,0] → [1,1] → [1,3] → [1,7] → [1,12] → [1,22]
              空     +1     +2补丁  +4补丁   +5吸收    +10吸收
```
> ⚠️ **致命陷阱**:`reach` 必须用 `long`!`n` 可达 `2^31-1`,翻倍会溢出 `int` 变负数,导致死循环。

**② 反悔贪心的「时光倒流」(LC 871 最低加油次数)**

一路开过去,把路过的每个加油站油量压入大根堆(先不加);油不够时才从堆里取最多的补加。

```text
        行驶 →→→→→→→→→→→→→→→→→→→→→→→→→→
        ⛽A(60)      ⛽B(30)      ⛽C(30)      ⛽D(40)      🎯target
油箱: 10 ────────────► 走到A前油尽?否 ──► 走到B?油尽!
                                          大根堆[A:60] → 弹出60补加 (次数=1)
                                          油箱回满 → 继续
                                    ────► 走到C?油尽!
                                          大根堆[B:30] → 弹出30补加 (次数=2)
反悔的本质: 沿途所有加油站都是「候选」, 只在必要时回头挑油最多的那个补加
堆维护的是「已路过但未使用」的机会集合
```

**③ 单调栈的「弹栈反悔」(LC 402 移掉 K 位数字)**

维护单调递增栈,遇到更小的字符且仍有删除额度就弹栈:

```text
num="1432219", k=3       目标: 删3位使剩余数最小
栈: []
 读'1' → 栈[1]
 读'4' → 4>1保留 → 栈[1,4]
 读'3' → 3<4 弹4(k=2) → 栈[1,3]
 读'2' → 2<3 弹3(k=1) → 栈[1,2]
 读'2' → 2=2保留 → 栈[1,2,2]
 读'1' → 1<2 弹2(k=0) → 栈[1,2,1]  (额度耗尽)
 读'9' → 直接入 → 栈[1,2,1,9]
结果: "1219"
每一次弹栈 = 一次「反悔」: 高位的大数字是负担, 有额度就在第一个逆序对处开刀
```

## 三、工业级编码与防御 (Implementation & Robustness)

### 3.1 核心引擎实现(遵循 Google Java Style)

**引擎一:静态扫描型 — 活动选择/区间调度(LC 435 无重叠区间)**

```java
/**
 * 求最少移除多少区间使剩余互不重叠。
 * 结构不变量: end 始终等于「已保留区间集合中最大的右端点」,
 *            它是对未来约束最宽松的边界(右端点越小,后续自由度越大)。
 */
int eraseOverlapIntervals(int[][] intervals) {
    if (intervals.length == 0) {
        return 0;
    }
    // 关键: 按右端点升序排序。用 Integer.compare 防止 (a-b) 相减溢出。
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[1], b[1]));

    int keptCount = 0;
    long lastEnd = Long.MIN_VALUE; // 用 long 防御 Integer.MIN_VALUE 边界

    for (int[] interval : intervals) {
        int start = interval[0];
        int end = interval[1];
        // 不变量维护: 只有当新区间左端点 >= 已保留的最大右端点时才保留,
        // 保留后立即更新 lastEnd, 保证不变量持续成立。
        if (start >= lastEnd) {
            keptCount++;
            lastEnd = end;
        }
        // 否则丢弃 —— 交换论证保证: 丢弃右端点更大的一定不劣。
    }
    return intervals.length - keptCount;
}
```

**引擎二:反悔贪心通用模板 — 堆维护已选集合(LC 871 最低加油次数)**

```java
/**
 * 从起点到 target,途中加油站 (position, fuel)。返回最少加油次数,不可达返回 -1。
 * 结构不变量: maxHeap 中始终是「已路过但尚未使用」的加油机会,
 *            currentFuel 始终 >= 0 (一旦将要 <0 就立刻反悔补加)。
 */
int minRefuelStops(int target, int startFuel, int[][] stations) {
    PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Collections.reverseOrder());
    int stops = 0;
    int currentFuel = startFuel;
    int stationIndex = 0;
    int numStations = stations.length;

    while (currentFuel < target) {
        // 把当前油量能到达的所有加油站的油量压入堆(记录机会,先不加)
        while (stationIndex < numStations && stations[stationIndex][0] <= currentFuel) {
            maxHeap.offer(stations[stationIndex][1]);
            stationIndex++;
        }
        // 约束被违反(开不到下一站/终点)却无油可补 → 无解
        if (maxHeap.isEmpty()) {
            return -1;
        }
        // 反悔: 从已路过的机会里挑「油最多」的那个补加, 单次收益最大
        currentFuel += maxHeap.poll();
        stops++;
    }
    return stops;
}
```

### 3.2 防御性编程与三大死亡测试 (Death Tests)

| # | 死亡测试 | 阴险之处 | 工业级防御 |
|---|---|---|---|
| **① 整型溢出** | `reach += reach`(补丁型)、`sum += a[i]`(滚雪球)在 `n≈2^31` 时翻倍溢出 `int` → 变负数 → 死循环或错误终止 | 数值在**中途**才溢出,小样例测不出来 | 累积量一律用 `long`;LC 330/1798/2789 血泪教训 |
| **② 比较器相减溢出** | 排序比较器写成 `(a,b)->a[1]-b[1]`,当端点为 `Integer.MAX/MIN` 时相减溢出,排序结果错乱 | JDK `Arrays.sort` 依赖比较器满足全序,溢出会破坏传递性,甚至抛 `IllegalArgumentException: Comparison method violates its general contract` | 一律用 `Integer.compare(a,b)` / `Long.compare`;LC 452 引爆气球必用 |
| **③ 端点相等语义歧义** | 「端点相等算不算重叠」因题而异:LC 435 不算(`>=`)、LC 452 算(`>` 才算新组)、LC 646 严格 `<` | 同一套区间模板,一个符号之差全盘皆错,且样例常常不覆盖边界接触 | 建模阶段就把「闭区间/开区间」语义钉死,写进注释;针对相等构造专门测试用例 |

**JDK 源码级防御范例**:`java.util.PriorityQueue` 在 `siftUp/siftDown` 中使用 `(size - 1) >>> 1` 而非 `(size-1)/2` 计算父节点,用**无符号右移**规避了极大堆下标相加时的符号问题;其扩容策略在容量 `< 64` 时翻倍、`>= 64` 时增长 50%,在「反悔风暴」(海量元素反复入堆出堆)下平摊掉扩容开销。

## 四、本质与权衡 (Essence & Trade-offs)

### 4.1 硬件亲和性与局部性原理

贪心范式在硬件层面的真实表现,取决于它承载在**数组**还是**堆**上:

- **数组扫描型贪心(LC 55、134、435)是 CPU 缓存的宠儿**。数组内存连续,一次线性扫描完美命中 **Cache Line**(通常 64 字节)的预取机制:CPU 预取器发现你顺序访问,会提前把后续数据搬进 L1/L2 缓存,几乎不产生缺页中断。这也是「数组遍历远快于链表遍历」的根源——链表节点散布在堆内存各处,每次跳转都是一次可能的缓存未命中(cache miss),甚至触发 TLB 缺失。
- **堆型贪心(LC 871、502、23)则要付出缓存代价**。二叉堆虽然用数组实现(下标连续),但 `siftDown` 时父子节点下标是 `i`、`2i+1`、`2i+2`——**跳跃式访问**,一旦堆较大就频繁跨 Cache Line,局部性远不如线性扫描。这就是为什么能用排序+扫描解决的问题,通常比用堆维护更快(虽然渐进复杂度都是 `O(n log n)`)。

> 举一反三:这正是**为什么 B+ 树比二叉搜索树更适合磁盘**——B+ 树一个节点存放上百个键,一次磁盘 I/O(远比内存慢)就能加载一整个节点,把「树高」压到极低,用空间的批量连续换取 I/O 次数的锐减。同一套「局部性优先」的智慧贯穿始终。

### 4.2 空间与时间的博弈

贪心为了换取时间,付出的空间代价因形态而异:

| 形态 | 时间 | 空间代价 | 博弈本质 |
|---|---|---|---|
| 静态扫描 | `O(n log n)` | `O(1)` 原地 | 几乎无代价,但适用面最窄 |
| 双向扫描(LC 135) | `O(n)` | `O(n)` 两个辅助数组 | **用两遍线性空间换取「双向约束」的解耦** |
| 堆型 / 反悔型 | `O(n log n)` | `O(n)` 堆开销 | 用堆的额外空间换取「动态取极值」的对数级速度 |
| 单调栈 | `O(n)` | `O(n)` 栈空间 | 用栈空间换取「字典序最优子序列」的一次成型 |

最深刻的一次博弈是 **LC 135 分发糖果的双向扫描**:一个元素同时受左右两侧约束,直接一次扫描无法兼顾。解法是**解耦**——从左到右扫一遍只满足「比左邻高就多给」,从右到左扫一遍只满足「比右邻高就多给」,最后 `candy[i] = max(left[i], right[i])`。用 `O(n)` 的额外空间,把一个双向难题拆成两个 `O(n)` 单向扫描,优雅至极。

## 五、工业落地与实战 (Industry & Practice)

### 5.1 真实世界架构:贪心的不可替代性

| 场景 | 贪心的应用 | 不可替代性 |
|---|---|---|
| **Huffman 编码(gzip/zip/JPEG)** | 每次合并频率最小的两棵子树(堆维护动态极值) | 贪心选择性质由「前缀码最优性」严格证明,是无损压缩的数学基石 |
| **网络路由 Dijkstra** | 每次从优先队列弹出当前距离最小的节点扩展 | OSPF 等路由协议的核心;堆是「待选集合取最优」的引擎 |
| **最小生成树 Kruskal/Prim** | 每次选最小权边(且不成环) | 网络布线、聚类;正确性由**拟阵理论(图拟阵)**统一保证 |
| **操作系统 EDF 实时调度** | 优先执行截止时间最早的任务(Earliest Deadline First) | 单处理器上 EDF 是最优的可调度性算法 |
| **Kafka / Netty 时间轮** | 分层时间轮 + 到期任务批量触发 | 用「桶」摊平定时器的 `O(1)` 插入,是延迟队列的贪心式近似 |
| **Redis / LevelDB** | 内存淘汰的 LRU/LFU 近似、Compaction 的 size-tiered 策略 | 用「当下最该淘汰/合并」的局部决策逼近全局最优 |

> 拟阵理论是贪心正确性的**统一框架**:若问题结构满足遗传性 + 交换性两条公理(构成一个拟阵),则贪心必然得到最优解,无需针对具体问题单独证明。Kruskal 的正确性本质上就是「图拟阵」的推论。

### 5.2 力扣试金石:必须用贪心才能最优的硬核题

**① LC 135 分发糖果(双向扫描的巅峰)**
> 相邻孩子评分高者拿更多糖,求最少总糖数。**应用姿势**:左右各扫一遍取 `max`。DP 需要 `O(n²)` 或复杂状态,贪心 `O(n)` 时间 `O(n)` 空间。安全性由交换论证保证:任何位置若糖数 `> max(left[i],right[i])` 都可无损调低,与「最优」矛盾。

**② LC 621 任务调度器(瓶颈框架的典范)**
> 相同任务间需冷却 `n`,求最短总时间。**应用姿势**:识别瓶颈=最高频任务。设最高频 `maxFreq`、达到最高频的任务数 `k`,则 `bottleneck = (maxFreq-1)*(n+1)+k`,答案 `= max(bottleneck, 总任务数)`。最高频任务像钉子钉死时间轴下界,其余任务只是往缝隙里塞。

**③ LC 316 去除重复字母(单调栈构造)**
> 去重使每字母只出现一次且字典序最小。**应用姿势**:单调栈 + `lastIndex` + `inStack`。栈顶比当前字符大、且后面还会出现,就弹栈。「能替换就替换」是构造字典序最小的核心,`O(n)` 一次成型。

**④ LC 407 接雨水 II(瓶颈 + 最值双维度)**
> 二维高度图能接多少水。**应用姿势**:小根堆维护「围墙边界」,每次弹出最矮的墙(瓶颈),邻格蓄水由当前最矮围墙决定,并以 `max(墙高,邻格高)` 作为新墙入堆。水永远从最矮的出口溢出——系统存水能力受限于最薄弱环节。

## 六、融会贯通与差异剖析 (Synthesis & Comparison)

### 6.1 终极对比:贪心 vs 动态规划

理解贪心边界最重要的一张表:

| 维度 | 贪心 | 动态规划 |
|---|---|---|
| 决策依据 | 只看**当前**局部最优 | 综合**所有**子问题的解 |
| 是否回溯 | 不回溯(反悔贪心是受控的有限撤销) | 隐式遍历所有状态转移 |
| 核心前提 | 贪心选择性质 + 最优子结构 | 重叠子问题 + 最优子结构 |
| 时间 | 通常 `O(n log n)` | 通常 `O(n·状态数)` |
| 空间 | `O(1)` ~ `O(n)` | `O(状态数)`,常更大 |
| 正确性 | **难,必须证明** | 状态转移正确即正确 |
| 何时用 | 局部最优可拼全局(如可切分背包) | 局部最优**无法**拼全局(如 0-1 背包) |

> 💡 **判别口诀**:**能贪就贪,贪不了就 DP。** 遇到「整数个/不可分/需凑组合数」先怀疑 DP;遇到「可排序后一次决策/可切分/可复用资源」先尝试贪心并证明。

### 6.2 正确性证明工具箱(贪心的灵魂)

DP 只要状态转移对了就对了,而贪心「看起来对」的策略极可能是错的——**必须证明或证伪**。四件武器按常用度排序:

1. **交换论证法(最常用)**:假设最优解 `OPT` 与贪心解 `G` 在某步不同,证明把 `OPT` 的选择替换成贪心的选择解不会变差,反复替换把 `OPT` 改造成 `G`。(活动选择、分发糖果、引爆气球均用此)
2. **归纳法**:证明「贪心保持了最优子结构」,从 `k=0` 推进到全局。
3. **反证法**:假设 `G` 非最优、存在更优 `OPT`,推出逻辑矛盾。
4. **拟阵理论(高级统一框架)**:若问题结构可形式化为拟阵,则贪心必然最优,揭示「为什么这么多贪心是对的」的深层原因。

> **实战建议**:竞赛/面试时**先花 30 秒尝试构造反例**——证伪一个错误贪心,比证明一个正确贪心快得多。如果 5 分钟想不出反例,这个贪心大概率是对的;如果找到反例,果断放弃转 DP。

### 6.3 四步诊断法(拿到贪心题的通用流程)

```text
┌────────────────────────────────────────────────┐
│ Step 1 识别瓶颈:答案的上/下界是什么?什么在限制答案? │
│ Step 2 寻找最值:排序/堆/极值能否简化决策?处理顺序重要吗? │
│ Step 3 确定不变量:每步之后什么性质仍成立?用什么结构维护? │
│ Step 4 验证安全性:能否用交换论证证明这步不亏?反证会否错过最优? │
└────────────────────────────────────────────────┘
```

### 6.4 记忆锚点

> 🎯 **贪心是「每一步都赌当下最优能拼出全局最优」——赌对了就是最快的解法,赌错了就是最隐蔽的 Bug。看到「区间」想排序键,看到「动态最值」想堆,看到「先选后悔」想反悔堆,看到「字典序」想单调栈,看到「最少步数覆盖」想 `maxReach`,看到「不可切分的组合」就放下贪心、拿起 DP。**

### 6.5 哲理总结

> **贪心的本质不是「贪」,而是「舍」——平衡的智慧在于容忍局部的不完美,以换取全局的最优;所有的快速求解,本质上都是在用一个单调收敛的标量,把不确定性一步步消除干净。你能证明「放弃某些可能性不会让答案变差」的那一刻,贪心才真正成立。**
