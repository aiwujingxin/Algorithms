# 堆、对顶堆与有序多重集：从极值维护到动态顺序统计

> **一句话总结：这个包用“只维护必要的偏序”换取极值查询效率，并沿着 `BinaryHeap → TopKHeap → AbstractDualHeap + LazyHeap` 逐步解决单极值、第 K 值和动态中位数问题；当需求升级为双端、邻近查询或严格实时删除时，再切换到基于 `TreeMap` 的 `TreeMultiset`。**

## 一、缘起与直觉（Origin & Intuition）

### 1. 痛点溯源与心智钩子

假设任务流不断到达，而系统每次都要处理“当前最紧急的任务”：

- 无序数组插入快，但找最值要扫描全部元素：`O(n)`。
- 有序数组找最值快，但插入要搬移元素：`O(n)`。
- 链表即使插入便宜，也缺少随机访问，寻找最值仍是 `O(n)`。
- 每次重新排序可以得到全序，但成本是 `O(n log n)`，而业务通常只问一个堆顶。

堆的历史必然性在于：**既然只关心极值，就没有必要维护所有元素之间的完整顺序。**

心智钩子：

- 看到“反复取当前最值 / 优先级” → `BinaryHeap`
- 看到“第 K 大 / Top K” → `TopKHeap`
- 看到“动态中位数 / 第 k 小” → 对顶堆
- 看到“滑动窗口 + 堆中间删除” → 懒删除
- 看到“双端极值 / floor / ceiling / 严格实时删除” → `TreeMultiset`

### 2. 物理映射与信息论

全排序维护的是任意一对元素的先后关系，信息量近似 `n log n`；堆只维护父子之间的偏序：

```text
最小堆：parent <= child
最大堆：parent >= child
```

它主动放弃“第二小在哪里”“遍历是否有序”等信息，只保证根节点一定是全局极值。少维护的信息，就是省下的时间。

完全二叉树又能压进连续数组，不需要真实指针：

```text
0-indexed:
parent(i) = (i - 1) / 2
left(i)   = 2 * i + 1
right(i)  = 2 * i + 2
```

对顶堆更进一步：它不维护完整排名，只维护一条动态分界线。较小部分放进最大堆，较大部分放进最小堆，两个堆顶共同描述中位数附近的局部秩序。

## 二、结构解剖与动态演变（Anatomy & Dynamics）

### 1. 核心 API 与时空矩阵

`n` 为当前有效元素数，`k` 为 Top K 容量。表中的“平均”包含常见输入下的表现；懒删除另行标注均摊成本。

| 结构与操作 | 最好 | 平均 | 最坏 | 额外空间 |
|---|---:|---:|---:|---:|
| `BinaryHeap.peek` | `O(1)` | `O(1)` | `O(1)` | `O(1)` |
| `BinaryHeap.push` | `O(1)` | `O(log n)` | `O(log n)` | 均摊 `O(1)` |
| `BinaryHeap.pop` | `O(1)` | `O(log n)` | `O(log n)` | `O(1)` |
| `BinaryHeap.heapify` | `O(n)` | `O(n)` | `O(n)` | `O(n)`，当前实现复制输入 |
| `MaxHeap.remove(value)` | `O(1)` | `O(n)` | `O(n)` | `O(1)` |
| `TopKHeap.offer` | `O(1)`，直接过滤 | `O(log k)` | `O(log k)` | 总计 `O(k)` |
| `TopKHeap.getKth` | `O(1)` | `O(1)` | `O(1)` | `O(1)` |
| `AbstractDualHeap.add` | `O(log n)` | `O(log n)` | `O(log n)` | 总计 `O(n)` |
| `AbstractDualHeap.remove` | 标记近似 `O(1)` | 均摊 `O(log n)` | 单次可清理多个墓碑 | 可能滞留失效元素 |
| `MidDualHeap.getMedian` | `O(1)` | 均摊 `O(1)` | 清理时可退化 | `O(1)` |
| `TreeMultiset.add/remove` | `O(log n)` | `O(log n)` | `O(log n)` | 总计 `O(n)` |
| `TreeMultiset.first/last` | `O(log n)` | `O(log n)` | `O(log n)` | `O(1)` |
| `TreeMultiset.floor/ceiling` | `O(log n)` | `O(log n)` | `O(log n)` | `O(1)` |

两个容易混淆的结论：

1. Floyd 自底向上建堆是 `O(n)`，不是 `O(n log n)`。靠近叶子的节点高度低，总工作量为  
   `Σ (节点数 × 节点高度) = O(n)`。
2. 懒删除的 `remove` 不是“严格单次 `O(log n)`”。标记通常很快，但一次 `clean` 可能连续清除多个失效元素；正确表述是：**每个元素最多入堆、出堆一次，因此整体均摊 `O(log n)`。**

### 2. 结构不变量

#### `BinaryHeap / MaxHeap`

1. 形状不变量：逻辑结构永远是完全二叉树。
2. 顺序不变量：任意父节点的优先级不晚于子节点。
3. 边界不变量：有效元素只位于 `[0, size)` 或 `[1, n]`。

#### `TopKHeap`

1. 堆中始终保留已见元素中最优的 `min(k, seen)` 个。
2. 堆顶永远是“已保留元素中最差的一个”。
3. 新元素不优于堆顶时，可以 `O(1)` 过滤。

#### `AbstractDualHeap`

1. 顺序不变量：`small` 中任意有效元素 `<= large` 中任意有效元素。
2. 大小不变量由子类定义：
   - 中位数：`small.size == large.size` 或 `small.size == large.size + 1`
   - 第 k 小：`small` 尽量保持 `k` 个有效元素
3. 计数不变量：逻辑 `size` 只统计有效元素，不统计尚未物理弹出的墓碑。

#### `LazyHeap`

```text
frequency[x] = x 当前仍有效的数量
delayed[x]   = x 已逻辑删除、等待物理弹出的数量
size         = Σ frequency[x]
```

`peek/pop` 前必须执行 `clean()`，否则堆顶可能是已删除元素。

#### `TreeMultiset`

1. `counts[key] > 0`，计数归零必须删除 key。
2. `size == Σ counts[key]`。
3. `TreeMap` 的红黑树不变量保证树高为 `O(log n)`。

### 3. 动态可视化

#### 上浮：新元素只沿祖先链修复

向最小堆 `[2, 5, 8, 9, 7]` 插入 `1`：

```text
数组初态: [2, 5, 8, 9, 7, 1]

             2
          /     \
         5       8
       /  \     /
      9    7   1

1 < 8，交换:
[2, 5, 1, 9, 7, 8]

             2
          /     \
         5       1
       /  \     /
      9    7   8

1 < 2，再交换:
[1, 5, 2, 9, 7, 8]

             1
          /     \
         5       2
       /  \     /
      9    7   8
```

树高是 `⌊log2 n⌋`，所以最多只走一条根路径。

#### 对顶堆：移动分界线，而不是重排全部元素

```text
有效序列: 1  3  5 | 7  9

small（最大堆）       large（最小堆）
       5                    7
     /   \                  |
    1     3                 9

中位数分界 = small.peek() / large.peek()
```

插入 `11` 后进入 `large`，若两边大小失衡，只移动一个堆顶：

```text
small: [5, 1, 3]       large: [7, 9, 11]
```

#### 懒删除：逻辑删除与物理删除分离

窗口移出元素 `3`，但 `3` 不在堆顶：

```text
PriorityQueue: [1, 3, 5, 7]
frequency:     {1=1, 5=1, 7=1}
delayed:       {3=1}
logical size:  3
physical size: 4
```

此时不扫描数组寻找 `3`。当 `3` 最终到达堆顶时：

```text
clean():
  poll 3
  delayed[3] -> 0
  remove delayed[3]
```

这相当于把“现在必须完成的随机删除”，改造成“未来顺手完成的堆顶删除”。

## 三、工业级编码与防御（Implementation & Robustness）

### 1. 核心引擎实现

下面是与本包 [`BinaryHeap`](./BinaryHeap.java) 一致的 0-indexed 下沉核心。关键不是交换本身，而是每轮都让“当前父节点与更优子节点比较”，从而恢复整条路径的不变量。

```java
private void siftDown(int parentIndex) {
  while (2 * parentIndex + 1 < size) {
    int betterChildIndex = 2 * parentIndex + 1;
    int rightChildIndex = betterChildIndex + 1;

    if (rightChildIndex < size
        && comparator.compare(
                elementAt(rightChildIndex), elementAt(betterChildIndex))
            < 0) {
      betterChildIndex = rightChildIndex;
    }

    if (comparator.compare(
            elementAt(parentIndex), elementAt(betterChildIndex))
        <= 0) {
      break;
    }

    swap(parentIndex, betterChildIndex);
    parentIndex = betterChildIndex;
  }
}
```

懒删除的核心是“有效计数”和“待删除计数”分离：

```java
public boolean remove(E element) {
  Integer validCount = frequency.get(element);
  if (validCount == null) {
    return false;
  }

  decrease(frequency, element, validCount);
  delayed.merge(element, 1, Integer::sum);
  size--;
  cleanTop();
  return true;
}

private void cleanTop() {
  while (!priorityQueue.isEmpty()) {
    E top = priorityQueue.peek();
    Integer delayedCount = delayed.get(top);
    if (delayedCount == null) {
      return;
    }

    priorityQueue.poll();
    if (delayedCount == 1) {
      delayed.remove(top);
    } else {
      delayed.put(top, delayedCount - 1);
    }
  }
}
```

代码中的防线：

- `Objects.requireNonNull`：避免比较器在深层调用处才触发难定位的 NPE。
- 弹出后清空数组槽位：避免对象仍被数组引用，阻止 GC 回收。
- 比较器控制方向：一份引擎同时支持最大堆和最小堆。
- `frequency + delayed` 双计数：正确处理重复值和重复删除。
- `clear()` 同时清空堆、有效计数和墓碑，避免状态撕裂。

### 2. 三个死亡测试

#### 死亡测试一：比较器整数溢出

错误写法：

```java
(a, b) -> a - b
```

`a = Integer.MAX_VALUE`、`b = -1` 时发生溢出，比较结果可能反向，直接破坏堆不变量。

防御：

```java
Integer::compare
```

JDK 集合要求比较器满足反对称性、传递性和一致性；违反约束时容器不会替业务纠正逻辑。

#### 死亡测试二：重复值跨分区删除

输入：

```text
add:    2, 2, 2, 3
remove: 2, 2, 2
```

如果只用 `Set` 标记删除，三个相同的 `2` 会被压成一个标记；如果仅凭当前分界判断元素属于哪一堆，也可能在重复值位于两边时删错计数。

防御：

- 删除表必须是 `Map<E, Integer>`，不能是 `Set<E>`。
- 每次删除只减少一个有效计数。
- 重平衡前后都只能信任已清理的堆顶。

#### 死亡测试三：墓碑堆积与并发访问

构造一个长时间滑动窗口，使被删除元素始终无法浮到堆顶，物理堆可能明显大于逻辑窗口。懒删除保证的是时间均摊，不自动保证物理容量始终等于有效元素数。

防御策略：

- 内存敏感或删除频繁时改用 [`TreeMultiset`](../other/impl/TreeMultiset.java)。
- 长生命周期服务可设置“物理大小 / 逻辑大小”阈值并周期性重建堆。
- 本包模板与 JDK `PriorityQueue` 都不是线程安全的；并发场景使用外部锁，或采用 `PriorityBlockingQueue`。但后者同样不提供高效任意删除。

另一个工业边界是超大数组扩容。JDK 集合会检查最大数组长度并在无法分配时尽早抛出 `OutOfMemoryError`；教学模板通常省略 `hugeCapacity` 逻辑，生产版本应补上容量溢出检查。

## 四、本质与权衡（Essence & Trade-offs）

### 1. 硬件亲和性与局部性

二叉堆的逻辑是树，物理上却是数组：

- 父子下标通过整数运算得到，不需要追逐左右指针。
- 数组连续存放引用，相邻层级更容易命中 CPU Cache Line。
- 建堆时自底向上的访问模式比红黑树的节点跳转更可预测。
- 节点没有 `parent/left/right/color` 等对象字段，GC 压力通常更低。

需要注意：Java 的 `Object[]` 连续的是“对象引用”，对象本体仍可能散落在堆内存中。若元素是整数且性能极端敏感，`int[]` 特化堆通常比 `BinaryHeap<Integer>` 更快，因为它避免装箱和对象间接寻址。

`TreeMap` 则是红黑树节点：

```text
Node {
  key, value,
  left, right, parent,
  color
}
```

它用更多指针和分支换来了有序导航能力。每次旋转或向下搜索都可能跨越多个内存位置，分支预测与缓存局部性通常不如数组堆。

还要明确能力边界：普通 `TreeMap` 只支持按 key 导航，不保存子树元素数量，因此不能直接按排名取第 k 个元素。使用有序集合求动态中位数时，仍需像对顶堆一样维护左右两个 `TreeMultiset`；若希望单树完成 `kth` 查询，则要在平衡树节点上增加子树大小，升级为顺序统计树。

### 2. 空间与时间的博弈

| 结构 | 付出的空间 | 换来的能力 |
|---|---|---|
| `BinaryHeap` | 动态数组预留容量 | `O(1)` 看顶、`O(log n)` 增删顶 |
| `TopKHeap` | 只保留 `k` 个元素 | 把 `O(n log n)` 全排序降为 `O(n log k)` |
| 对顶堆 | 两个堆 | 用两端极值描述动态中位数 |
| 懒删除 | `frequency`、`delayed` 与墓碑 | 避免堆中间的 `O(n)` 定位 |
| `TreeMultiset` | 红黑树节点与计数 | 最坏 `O(log n)` 实时删除、双端和邻近查询 |

本包 `BinaryHeap` 扩容时容量翻倍，减少了扩容次数，但峰值可能保留接近一倍的空槽。JDK `PriorityQueue` 使用更细致的增长策略，在扩容频率和内存浪费之间做折中。

## 五、工业落地与实战（Industry & Practice）

### 1. 真实世界架构

#### JDK `PriorityQueue`

JDK 使用数组二叉最小堆实现通用优先队列。它是本包 `BinaryHeap` 最直接的工业参照：比较器控制优先级，插入和弹顶为 `O(log n)`。

#### JDK `ScheduledThreadPoolExecutor`

内部延迟队列按任务触发时间维护最小值。调度器最关心的是“下一个到期任务”，不需要把所有任务完全排序，因此堆比有序数组更合适。

#### Kubernetes Scheduler

调度队列需要优先处理更紧急或更高优先级的 Pod。工程实现除了堆，还会叠加退避队列、不可调度队列和事件唤醒机制；堆负责的是核心的动态优先级选择。

#### 图算法与检索系统

Dijkstra、Prim、A* 和多路归并都反复执行“取当前代价最小状态”。堆把每轮全局扫描从 `O(n)` 降到 `O(log n)`，是稀疏图算法达到工程可用复杂度的关键部件。

#### 数据库 Top N

查询只要求 `ORDER BY ... LIMIT k` 时，不必对全部结果完整排序。固定容量堆只保留当前最优 `k` 条记录，可将排序阶段从 `O(n log n)` 降到 `O(n log k)`。

### 2. 力扣试金石

#### LeetCode 23：合并 K 个升序链表

- 把每条链表当前头节点放入最小堆。
- 每次弹出全局最小节点，再把它的后继入堆。
- 总复杂度 `O(N log k)`，堆中最多 `k` 个节点。

对应题型：K 路归并。

#### LeetCode 295：数据流的中位数

- `small` 最大堆保存较小一半。
- `large` 最小堆保存较大一半。
- 插入 `O(log n)`，查询中位数 `O(1)`。

对应模板：[`MidDualHeap`](./MidDualHeap.java)。

#### LeetCode 480：滑动窗口中位数

- 在对顶堆基础上加入懒删除。
- 窗口右端入堆，左端只做逻辑删除。
- 查询前清理堆顶墓碑，并维持大小不变量。

对应实现：`LeetCode480_dualheap`。这是检验“重复值计数、分区判断、延迟清理、重平衡”是否同时正确的综合题。

#### I. Top K —— 有界过滤器

- **建模思想**：维护一个大小恒为 `k` 的堆。求「第 K 大」用**小顶堆**（堆满后新元素只有大于堆顶才替换），求「第 K 小」用大顶堆，方向与所求恰好相反。
- **本质**：用一个反向的定容堆，把 `n - k` 个不可能进入答案的元素在 `O(1)` 时刻过滤掉，从而把全排序的 `O(n log n)` 降为 `O(n log k)`。堆顶天然就是“当前保留集合里最差的一个”，也就是第 K 值。
- **代表题分析**：
  - **215 数组中的第 K 个最大元素**：小顶堆存当前最大的 `k` 个数，堆顶即第 K 大。遍历一遍，堆满后 `nums[i] > peek()` 才替换堆顶。`O(n log k)`，空间 `O(k)`。
  - **347 前 K 个高频元素**：先用哈希表统计频次，再以“频次”为比较键维护大小为 `k` 的小顶堆，最终堆内即前 K 高频。`O(n log k)`。
  - **973 最接近原点的 K 个点**：以“到原点距离平方”为键的**大顶堆**存 `k` 个点，新点比堆顶近就替换——保留最近 `k` 个的等价写法是弹出最远的。`O(n log k)`。

#### II. 滑动窗口 —— 懒删除

- **建模思想**：窗口右移时入堆；取堆顶前先判断它是否已滑出窗口——存 `[值, 下标]` 判过期，或用 `frequency + delayed` 双计数做延迟删除，过期元素只在浮到堆顶时才真正弹出。
- **本质**：堆无法 `O(log n)` 删除中间元素，于是把“此刻必须完成的随机删除”改写成“将来顺手完成的堆顶删除”。每个元素至多入堆、出堆一次，整体均摊 `O(log n)`；代价是物理堆里可能暂存墓碑。
- **代表题分析**：
  - **239 滑动窗口最大值**：大顶堆存 `[值, 下标]`，取堆顶前循环弹出下标已越界（`idx <= i - k`）的元素。堆顶即窗口最大值。均摊 `O(n log n)`；用单调队列可优化到 `O(n)`，但堆写法最直白。
  - **480 滑动窗口中位数**：对顶堆 + 懒删除。右端入堆、左端逻辑删除，查询前 `clean()` 清墓碑并重平衡，堆顶给出中位数。注意用 `Map<E,Integer>` 计数以正确处理重复值。

#### III. K 路归并 —— 活跃前沿

- **建模思想**：把 `k` 个有序序列的当前头部放进堆，每次弹出全局最小，再把它的后继补进堆，弹一入一，直到取够。
- **本质**：堆在任意时刻只握有“所有活跃序列的当前最小者”这条前沿，而不是全部元素。取 `m` 个元素为 `O(m log k)`，空间只需 `O(k)`——这是外部排序、多路合并能落地的根本原因。
- **代表题分析**：
  - **23 合并 K 个升序链表**：`k` 个链表头入小顶堆，每次弹出最小节点接到结果尾部，再把它的 `next` 入堆。堆中最多 `k` 个节点，`O(N log k)`。
  - **378 有序矩阵中第 K 小**：把每行行首入堆（存 `[值, 行, 列]`），弹出后推入同行右邻，弹 `k` 次即得第 K 小。`O(k log m)`；也可对值域二分。
  - **373 查找和最小的 K 对**：堆按“对和”排序，先入 `(0, j)` 系列，每弹出 `(i, j)` 就推入 `(i+1, j)`，弹一入一避免枚举全部 `m*n` 对。

#### IV. 区间与资源调度 —— 最早可用资源

- **建模思想**：先按开始时间排序，用小顶堆维护“各资源的释放 / 结束时刻”；新任务到来时，若堆顶资源已释放就复用，否则新开资源。
- **本质**：堆顶恒为“最早空闲的那份资源”，把 EDF（最早截止优先）/ 会议室模型里反复的“找最早可用”降到 `O(log n)`，贪心地复用资源以最小化资源数量。
- **代表题分析**：
  - **253 会议室 II**：会议按开始时间排序，小顶堆存各房间的“结束时间”。新会议开始时间 `>=` 堆顶则复用（弹出旧结束时间），否则新开房间。堆的最大尺寸即所需房间数，`O(n log n)`。
  - **1845 座位预约管理系统**：小顶堆维护“已释放的可用座位号”，`reserve` 优先取堆顶最小号、堆空时发新号，`unreserve` 把座位号还回堆。每次操作 `O(log n)`。

#### V. 贪心选择（反悔贪心）—— 已选集合的最差项

- **建模思想**：每一步用堆取当前最优做决策；一旦后续约束被违反，就从**已选集合**里弹出“最差的一个”反悔替换掉。
- **本质**：反悔贪心的核心是“动态维护已做选择中的极值”，堆恰好把这个操作降到 `O(log n)`。它实现的是一种“时光倒流”——允许撤销此前看似最优、如今成为瓶颈的选择（详见 [`Greedy`](../../algorithms/greedy/Greedy.java) 第 VI 章）。
- **代表题分析**：
  - **630 课程表 III**：按截止时间排序，依次“先修再说”并把时长压入大顶堆；一旦累计时长超过当前截止，就弹出**耗时最长**的已选课程反悔。堆保证被撤销的总是最亏的一门，`O(n log n)`。
  - **502 IPO**：项目按启动资本排序，将当前资本可解锁的项目利润推入大顶堆，每轮取堆顶最大利润执行，更新资本后再解锁更多项目。堆维护“当前可做项目中的最大收益”。
  - **1962 移除石子使总数最小**：大顶堆每次取最多的一堆减半再放回，重复 `k` 次。堆保证每步都作用在当前最大堆上，`O(k log n)`。

#### VI. 图搜索 —— 全局最小代价扩展

- **建模思想**：小顶堆按“当前累计代价”出队，取出后松弛其邻边并把更新后的邻点入堆。瓶颈类问题把“累加”换成“取路径上的最大边”。
- **本质**：堆保证每次扩展的都是全局代价最小的节点，这正是 Dijkstra / Prim 的正确性前提。松弛式 `dist = min(dist, d + w)` 与瓶颈式 `dist = min(dist, max(d, w))` 只是聚合函数不同，堆的角色不变。
- **代表题分析**：
  - **1631 最小体力消耗路径**：把“路径代价”定义为途经相邻格高差的最大值，小顶堆按此瓶颈值出队，第一次到达终点即答案。`dist = min(dist, max(dist, |Δh|))`，`O(mn log(mn))`。
  - **407 接雨水 II**：木桶效应——从最外圈围墙（小顶堆按高度）向内收缩，每次弹出最矮的墙，邻格蓄水量由当前最矮围墙决定，并以 `max(墙高, 邻格高)` 作为新墙入堆。
  - **787 K 站中转内最便宜的航班**：带层数限制的最短路，堆节点存 `[累计花费, 城市, 剩余中转次数]`，按花费出队，剩余次数为 0 则不再扩展。

#### VII. 优先级模拟 —— 取顶、处理、回填

- **建模思想**：把带优先级的元素放进堆，反复取堆顶处理；处理过程中若产生新元素（如冷却后重新可用、时间线上的下一条），再入堆。
- **本质**：堆作为优先级队列，天然表达“谁最紧急 / 最优先谁先出”的调度语义。重构字符串、任务冷却、多用户时间线合并，都是“取顶—处理—回填”这一循环的变体。
- **代表题分析**：
  - **767 重构字符串**：大顶堆按剩余频次排序，每次取出频次最高且**与上一个不同**的字符追加，用完暂存、下轮再放回，实现相邻不重复的隔板效果。若某字符频次超过 `(n+1)/2` 则无解。
  - **355 设计推特**：`getNewsFeed` 时把关注对象各自最新推文入堆做多路归并，弹十次取最近十条。堆按推文时间戳排序，弹一条就补该用户的上一条。
  - **1405 最长快乐字符串**：大顶堆按 `a/b/c` 剩余数量排序，每次取最多且不会造成三连的字符，取不了就退而取次多的，贪心拼出最长串。

#### VIII. 动态顺序统计 —— 对顶堆维护分界

- **建模思想**：大顶堆存较小的一半、小顶堆存较大的一半，通过再平衡让分界（两个堆顶）恰好落在中位数或第 K 小的位置。
- **本质**：两个堆把“动态顺序统计”这个看似需要全序的问题，拆解成“两侧各查一个局部极值”。它并不维护完整排名，只维护一条会移动的分界线；配合懒删除即可支持滑动窗口——这正是 [`AbstractDualHeap`](./AbstractDualHeap.java) 的设计动机。
- **代表题分析**：
  - **295 数据流的中位数**：`small` 大顶堆存较小一半、`large` 小顶堆存较大一半，维持 `small.size` 等于或比 `large` 多一。奇数取 `small` 堆顶，偶数取两堆顶均值。插入 `O(log n)`、查询 `O(1)`，见 [`MidDualHeap`](./MidDualHeap.java)。
  - **480 滑动窗口中位数**：在 295 的对顶堆上叠加懒删除处理窗口左端移除，是本类与「滑动窗口」类的交汇点。
  - **2653 滑动子数组的美丽值**：需要窗口内的“第 x 小”，用对顶堆让 `small` 恰好保留最小的 `x` 个，堆顶即第 x 小，见 [`KthDualHeap`](./KthDualHeap.java)。

## 六、融会贯通与差异剖析（Synthesis & Comparison）

### 1. 二叉堆 vs `TreeMap` 有序多重集

| 维度 | 二叉堆 / 对顶堆 | `TreeMultiset` |
|---|---|---|
| 底层建模 | 完全二叉树 + 父子偏序 | 红黑树 + 全局键有序 |
| 物理布局 | 连续数组引用 | 分散树节点 |
| 看单端极值 | `O(1)` | `O(log n)` |
| 插入 | `O(log n)` | `O(log n)` |
| 任意删除 | 原生 `O(n)`；懒删除均摊优化 | 最坏 `O(log n)` 实时删除 |
| 双端极值 | 通常需要两个堆 | 单结构支持 |
| `floor/ceiling` | 不支持 | `O(log n)` |
| 重复值 | 可直接入堆；懒删除需计数 | `key -> count` |
| 常数与缓存 | 通常更优 | 通常更高 |
| 内存上界 | 懒删除可能暂存墓碑 | 与有效 key 数同步 |
| 最适场景 | 高频单端极值、Top K、中位数 | 范围、邻近、双端、频繁随机删除 |

选择算法：

```text
只取一个方向的最值？
  └─ 是 → BinaryHeap

只保留最优 k 个？
  └─ 是 → TopKHeap

需要动态中位数 / 第 k 小？
  ├─ 删除少或可懒删除 → AbstractDualHeap
  └─ 删除频繁且内存上界敏感 → 两个 TreeMultiset 维护分界

需要 floor / ceiling / 区间导航？
  └─ 是 → TreeMultiset
```

### 2. 包内模板之间的差异

- `MaxHeap` 回答“堆是怎么工作的”，适合学习和手写。
- `BinaryHeap` 回答“如何复用一套堆引擎”，适合通用模板。
- `TopKHeap` 回答“如何只保留有用的 k 个候选”，本质是有界过滤器。
- `AbstractDualHeap` 回答“如何用两个局部极值描述动态秩序”。
- `MidDualHeap` 与 `KthDualHeap` 只改变大小不变量，不重复实现底层删除机制。
- `TreeMultiset` 不是堆，而是当堆的偏序能力不足时使用的有序集合替代方案。

### 3. 记忆锚点

> **堆像一支只露出最优候选人的队伍：它不关心所有人怎么排，只保证下一位该出场的人永远站在门口。**

### 4. 哲理总结

> **高效数据结构的本质不是保存更多秩序，而是准确判断哪些秩序根本不值得维护。**
